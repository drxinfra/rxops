# Чек-лист ревью прикладного кода по производительности и надёжности

Для ревью изменения (merge request, новая версия решения) или аудита решения целиком. Каждый пункт: вопрос к коду и что считать нарушением. Отвечайте по файлам, на которые указали логи и `review_scan.py`, затем по остальным изменённым. Образцы кода: `patterns.md`.

## Данные и запросы

- [ ] **Запросы в цикле.** Нет `GetAll`, `Get(id)`, `SQL` и Remote-вызовов внутри `foreach`, `for`, `while`, в том числе через вызываемую функцию. Нарушение: число запросов растёт с размером коллекции.
- [ ] **Материализация.** `ToList()`, `ToArray()` только по заранее отфильтрованной небольшой выборке; большие выборки остаются `IQueryable` (справка RX 25.2: sds_poluchenie_bolshogo_obema_dannuh.htm).
- [ ] **Фильтр до ToList.** `Where`, `Any`, `Count` стоят до `ToList()`, а не после.
- [ ] **GetAll без фильтра.** Нет `GetAll()` по растущим таблицам (документы, задачи, задания, история) без `Where`; для справочников на десятки строк допустимо.
- [ ] **Проекция.** Нужны одно-два свойства: `Select` в структуру, а не сущности целиком.
- [ ] **Жадная загрузка.** Свойства, которые читаются для каждого элемента списка (в том числе в доступности действий), помечены «Загружать значение сразу» (справка: sds_zhadnaya_zagruzka_svoistv.htm).
- [ ] **Большие списки.** Для списков на миллионы записей предварительная фильтрация (`PreFiltering`) по базовым критериям, затем `Filtering` (справка: sds_indeksu.htm, sds_parametry_filtracii.htm).
- [ ] **Отчёты.** Тяжёлые отчёты не строятся по всей базе без ограничения периода (справка: dds_optimizaciya_postroeniya_otchetov.htm).

## Индексы

- [ ] Частые фильтры новых списков, папок (в том числе вычисляемых), виджетов, отчётов и фоновых выборок покрыты индексом.
- [ ] Индекс объявлен в решении (SQL-запрос модуля и создание при инициализации, справка RX 25.2: sds_indeksu.htm), а не создан руками в базе.
- [ ] В составном индексе первыми колонки из `WHERE`, дальше по убыванию уникальности; имя не длиннее 63 символов (ограничение PostgreSQL) и говорит о таблице и полях.
- [ ] Нет индексов «на всякий случай» и по маленьким таблицам: каждый индекс замедляет запись и растит WAL.
- [ ] Колонки внешних ключей, по которым удаляют или меняют родителя, проиндексированы: иначе ожидания и дедлоки.
- [ ] Индекс подтверждён планом запроса на данных продуктивного объёма.

## Асинхронные обработчики

- [ ] **Повтор задан осознанно**: «с увеличением интервала» или «через равные промежутки», лимит повторов разумный (справка: sungerodev_baseeditor_asynchandlerstab.htm).
- [ ] **Занятая запись не исключение.** Проверка `Locks.GetLockInfo(...).IsLockedByOther` или `TryLock`, затем `args.Retry = true` и понятный `args.RetryReason`.
- [ ] **Идемпотентность.** Повторный запуск с теми же параметрами не задвоит результат: не создаст вторую задачу, не выдаст права дважды, не отправит письмо снова. Проверка «уже сделано» в начале.
- [ ] **Нет Thread.Sleep и ожиданий** внутри обработчика: вместо этого повтор с `NextRetryTime`.
- [ ] **Параметры простых типов**, файлы через потоки, не массивы байт.
- [ ] **Не на каждое сохранение.** Вызов из событий сохранения стоит под условием изменения нужных свойств (справка: dds_vyzov_ao_sokhranen_kartochki.htm).
- [ ] **Длинная работа порциями**: обработчик берёт порцию, проверяет остаток и вызывает переповтор; тяжёлые и длинные обработчики вынесены на отдельный экземпляр Worker параметрами `ASYNC_HANDLERS_PROCESSING` и `ASYNC_HANDLERS_EXCLUDED` (справка: dds_zapusk_bolshogo_kolichestva_dlitelnykh_ao.htm, inst_config_worker.htm).
- [ ] **Транзакция проверяется**: если транзакция внутри обработчика не выполнилась, обработчик сам не повторится; результат `Transactions.Execute()` проверяется.

## Фоновые процессы

- [ ] Обработка порциями, каждая запись или порция в своей транзакции: ошибка одной не откатывает весь запуск (справка: sungerodev_baseeditor_jobstab.htm).
- [ ] После неудачной транзакции сущности перечитываются из репозитория, а не используются повторно (справка: om_rabota_s_tranzaktsiyami_transactions.htm).
- [ ] Время выполнения на продуктивном объёме меньше периода расписания; расписание не совпадает с пиком пользователей.
- [ ] Блокировки берутся на запись и на короткое время, не на весь запуск.
- [ ] Массовые удаления и пересчёты не в рабочее время.

## Блокировки и транзакции

- [ ] Перед программным изменением сущности ставится блокировка (справка: om_blokirovki.htm), `TryLock` вместо `Lock` там, где запись может быть занята, `Unlock` в `finally`.
- [ ] Нет `Transactions.Execute()` там, где транзакция уже открыта платформой: события «До сохранения (в транзакции)» и «После сохранения (в транзакции)», Remote-функции, вызванные с клиента, функции инициализации, блоки схем задач, POST-функции интеграции.
- [ ] Порядок обращения к одним и тем же записям в разных местах кода одинаковый (иначе дедлоки 40P01).
- [ ] Конфликт «Запись была изменена в другой транзакции» в фоновом коде обрабатывается повтором.
- [ ] Транзакции короткие: внутри нет HTTP-вызовов во внешние системы и обработки тысяч элементов по одному (`idle in transaction` в базе).

## Ресурсы и клиент

- [ ] `SQL.CreateConnection()` и команды только в `using`; где можно, `SQL.GetCurrentConnection()` (справка: om_rabota_sql.htm).
- [ ] Значения в SQL через `SQL.AddParameter`, а не сложением строк.
- [ ] Табличная часть не рассчитана больше чем на 2000 строк (для RX 4.7 и выше); больше: отдельный справочник.
- [ ] Контрол состояния не строится по огромным спискам.
- [ ] С клиента одна серверная функция с атрибутом `Remote` на действие вместо нескольких; чистые функции чтения `Remote(IsPure = true)` (справка: sds_obedinenie_vuchislenii.htm).
- [ ] Тяжёлые вычисления не в клиентском коде и не в клиентских событиях показа и обновления формы: там они повторяются на каждое действие пользователя.
- [ ] Большие коллекции не держатся в статических полях и кэшах без ограничения: память сервиса растёт до перезапуска.
- [ ] Не отключён таймаут операций веб-сервера ради долгой функции (справка: sds_optimizaciya_processov.htm): долгое уходит в асинхронный обработчик.

## Проверяемость

- [ ] В обработчиках и фоновых процессах `RetryReason` и логи с идентификаторами записей, без паролей и персональных данных.
- [ ] Для изменения есть сценарий проверки на тестовом контуре и критерий приёмки (`acceptance.md`).
