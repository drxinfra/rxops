# review_scan.py: правила и ограничения

Статический просмотр исходников решения Directum RX (C#) на рискованные места. Только чтение, без сборки, без сети, без стенда. Python 3.6+, стандартная библиотека.

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/review_scan.py <папка решения>                 # все правила
python3 ${CLAUDE_SKILL_DIR}/scripts/review_scan.py <папка> --rule query-in-loop,getall-unfiltered
python3 ${CLAUDE_SKILL_DIR}/scripts/review_scan.py <папка> --json > scan-before.json
python3 ${CLAUDE_SKILL_DIR}/scripts/review_scan.py --list-rules
```

Читает `*.cs`, пропуская `bin/`, `obj/`, `.git/` и `*.g.cs`. Перед поиском убирает комментарии и содержимое строк, поэтому SQL внутри строки и закомментированный код не дают находок. Объявления индексов (`CREATE INDEX`, `CreateIndex...(`) считаются во всех текстовых файлах решения, включая строки и запросы модулей. Строка кода под находкой проходит через маскировщик. Коды: 0 нет WARN и CRIT, 1 есть, 2 не удалось проверить (нет пути, нет `*.cs`, неверный ключ).

## Правила

| Правило | Уровень | Что ищет | Частые ложные срабатывания |
|---|---|---|---|
| `sql-connection-no-using` | CRIT | `SQL.CreateConnection()` не в `using (...)` и не в `using var` | соединение отдаётся наружу и закрывается вызывающим (всё равно стоит переписать) |
| `query-in-loop` | WARN | `GetAll(`, `.Get(`, `SQL.CreateConnection`, `Execute*` или `Where(...).ToList()` внутри цикла | `Get` у словаря или своего класса; цикл на две-три итерации |
| `remote-in-loop` | WARN | `.Remote.Функция(` внутри цикла | цикл заведомо из пары элементов |
| `getall-unfiltered` | WARN | `GetAll()` с пустыми скобками, сразу материализованный (`ToList`, `ToArray`...) или в заголовке `foreach` | маленькие справочники (виды документов, валюты) |
| `tolist-then-filter` | WARN | `ToList().Where(...)` и подобное | коллекция уже маленькая и нужна в памяти целиком |
| `thread-sleep` | WARN | `Thread.Sleep(`, `Task.Delay(...).Wait()` | осознанная пауза в инструменте миграции вне сервисов RX |
| `lock-no-unlock` | WARN | `Locks.Lock`/`TryLock` в функции без `Locks.Unlock` или без `finally` | блокировка намеренно снимается в другой функции |
| `lock-hard-in-handler` | WARN | `Locks.Lock(` в асинхронном обработчике или в `*Jobs.cs` | запись заведомо не редактируется людьми |
| `async-no-retry` | INFO | асинхронный обработчик (параметр `...AsyncHandlerInvokeArgs...`) без `args.Retry`, `RetryReason`, `NextRetryTime` | обработчик не трогает общие записи и не может встретить блокировку |
| `executeasync-on-save` | WARN | `.ExecuteAsync(` в `BeforeSave`, `Saving`, `Saved`, `AfterSave` не под `if` | условие проверяется в вызываемой функции |
| `nested-transaction` | WARN | `Transactions.Execute(` в `Saving`, `Saved`, в функции с атрибутом `Remote`, в `*Initializer.cs` | Remote-функция, которая вызывается только с сервера |
| `sql-concat` | INFO | `CommandText` собирается через `+`, `+=` или `$"..."` | подстановка имени таблицы из констант |
| `no-index-declared` | INFO | во всём решении ни одного объявления индекса при наличии `GetAll(x => ...)` | индексы объявлены способом, которого скрипт не знает |

## Чего скрипт не видит

- Запрос в функции, вызванной из цикла: цикл и запрос в разных функциях или файлах. Ищите по чек-листу и по числу вызовов запроса в `pg_stat_statements`.
- Нужен ли индекс и выбирает ли его планировщик: это только план запроса на данных продуктивного объёма.
- Идемпотентность обработчика, порядок блокировок в разных местах кода, длительность транзакций.
- Метаданные (`.mtd`): табличные части, «жадная» загрузка, настройки повторов обработчиков. Их смотрят в среде разработки или в `.mtd` глазами.
- Код, сгенерированный платформой, и код стандартного решения вендора, если его нет в папке.

## Как читать результат

1. Сначала CRIT, затем WARN в файлах, на которые указали логи и метрики.
2. Каждую находку открыть и проверить по чек-листу: это правда большая выборка, правда цикл по сотням элементов?
3. Подтверждённое оформить для разработчиков: файл, строка, правило, почему это плохо, какой замер это показывает.
4. После правки прогнать скрипт ещё раз с `--json` и сравнить: находка ушла, новых не появилось.
