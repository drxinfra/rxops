# Чек-лист обновления Directum RX: 44 пункта, 7 этапов

Тот же список, что на странице https://drxinfra.ru/upgrade-checklist.html, своими словами и с
подсказками, чем проверить. Как пользоваться:

- в начале заполните шапку: с какой версии, на какую, когда окно;
- отмечайте `[x]` по ходу; пункты «если есть» (интеграции, единый вход, дежурные мониторинга)
  отметьте сразу, если у пользователя их нет, иначе процент выполнения врёт;
- в конце отдайте список с отметками: это отчёт о работах и план следующего обновления.
  Допишите, что пошло не по плану.

```
Обновление Directum RX
Версия: <с версии> → <на версию>
Окно работ: <дата и время>
Отмечено: N из 44
```

Справа после «→» сказано, чем проверить пункт. `preflight` значит
`python3 ${CLAUDE_SKILL_DIR}/scripts/preflight.py` с указанными ключами.

## 1. За две недели до окна

Что узнать и согласовать, пока есть время передумать.

- [ ] 1. Прочитать, что меняется в новой версии, и её требования к ОС, СУБД, .NET, RabbitMQ и
  Elasticsearch. → документ вендора «Типовые требования к аппаратному и программному обеспечению»
- [ ] 2. Сверить своё окружение с требованиями. Если СУБД или поиск тоже надо обновить, это
  отдельные работы до окна.
- [ ] 3. Составить список доработок и интеграций: что пересобирать, кто разработчик, кто проверит.
- [ ] 4. Отдать разработчикам новую версию платформы: пересборка доработок часто дольше самого
  обновления. → справка: пакет собирают на новой версии
- [ ] 5. Выбрать окно и согласовать его с бизнесом, сразу с временем на откат.
- [ ] 6. Назначить одного человека, который решает про откат и на связи всё окно.
- [ ] 7. Проверить место под бэкап базы перед работами и под файлы двух версий одновременно.
  → preflight `--path ПУТЬ=ГБ`

## 2. Репетиция на тестовом контуре

Пройти обновление целиком там, где ошибка ничего не стоит.

- [ ] 8. Поднять тестовый контур из свежего бэкапа прода. Не поднялся из бэкапа: не получится и
  откат. → скил `rx-backup-check`
- [ ] 9. Обновить тестовый контур по шагам, записывая каждый шаг и его длительность: этот журнал
  станет планом на окно. → `script -a ~/rx-update-ДАТА.log`
- [ ] 10. Замерить, сколько идёт конвертация базы: от этого зависит длина окна.
  → preflight `--post --launcher-dir` (длительность по DBConverter.log)
- [ ] 11. Опубликовать пересобранные доработки и пройти основные сценарии: задание, документ,
  согласование, поиск. → `references/smoke.md`
- [ ] 12. Если есть: проверить интеграции с внешними системами (почта, обмен с учётными
  системами, единый вход).
- [ ] 13. Отдать разработчикам список того, что сломалось, до окна, а не после.
- [ ] 14. Замерить откат: восстановление базы и хранилища из бэкапа и запуск прежней версии.
  → `references/rollback.md`

## 3. План отката

Пишется до работ; решение принимается по списку, а не на месте.

- [ ] 15. Записать точку невозврата. Обычно это пуск пользователей: после него в базе появятся
  новые данные.
- [ ] 16. Записать условия отката, например «конвертация идёт вдвое дольше, чем на репетиции».
- [ ] 17. Проверить, что работы плюс откат помещаются в окно: окно 6 часов, откат 2, на работы 4.
- [ ] 18. Сохранить установочные файлы и настройки текущей версии, чтобы откат не зависел от
  того, доступен ли сайт вендора. → справка: `config.yml`, `haproxy.cfg`, данные RabbitMQ

## 4. Накануне

Последняя проверка готовности.

- [ ] 19. Предупредить пользователей за день и ещё раз за час. → всплывающее сообщение в
  веб-клиенте
- [ ] 20. Убедиться, что ночной бэкап сделан: это запасной вариант, если бэкап в окне не выйдет.
  → preflight `--backup-dir КАТАЛОГ --backup-max-age 26`
- [ ] 21. Скачать дистрибутив новой версии и сверить контрольные суммы. → `sha256sum`
- [ ] 22. Проверить доступы: серверы, база, консоль администратора, пароль шифрования
  `config.yml`. Вспоминать пароль в два часа ночи дорого.
- [ ] 23. Если есть: предупредить дежурных мониторинга или выключить уведомления на окно.

- [ ] 29. Опубликовать пересобранные доработки, все пакеты за один раз.

## 6. Проверки до пуска пользователей

Вход ещё закрыт: если что-то не так, решение об откате ничего не стоит.

- [ ] 31. Все сервисы запущены, в журналах нет повторяющихся ошибок.
  → preflight `--post --before --status-dir --launcher-dir`, скил `rx-logs`
- [ ] 32. Вход работает так, как входят пользователи, включая единый вход по доменной учётке.
- [ ] 33. Задание создаётся, отправляется и приходит исполнителю.
- [ ] 34. Документ открывается, новая версия сохраняется.
- [ ] 35. Поиск находит документ, созданный после обновления: индексация работает, а не просто
  лежит старый индекс. → скил `rx-elasticsearch`
- [ ] 36. Очереди брокера разбираются, у каждой есть потребитель. → скил `rx-rabbitmq`
- [ ] 37. Если есть: интеграции с внешними системами отвечают.
- [ ] 38. Мониторинг видит новую версию, алерты не молчат и не шумят.
- [ ] 39. Открыть вход пользователям. → выключить режим технического обслуживания

- [ ] 41. Следить за ростом очередей и ошибками в журналах.

## Частые вопросы

- **Можно ли без репетиции.** Можно, если готовы узнать время конвертации и поломки доработок
  прямо в окне. Репетиция даёт порядок, который точно работает, время этапов и список поломок,
  а заодно проверяет бэкап.
- **Пропущено несколько версий.** По справке целевой версии посмотрите, можно ли перейти сразу
  или нужны промежуточные (`references/versions.md`). Каждая промежуточная версия добавляет своё
  преобразование базы, его время тоже замеряют на репетиции.
- **Кто решает про откат.** Один человек, названный заранее, по записанным условиям. В четыре утра
  тянет «ещё немного починить», и так окно заканчивается без новой версии и без старой.
