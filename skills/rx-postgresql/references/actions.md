# Команды, которые меняют систему

Каждую команду сначала показывают пользователю вместе с тем, что она сделает, чем грозит и как откатить, и выполняют только после явного согласия. Перед действием над сессией проверьте, что pid всё ещё та же сессия: номера процессов переиспользуются.

```sql
SELECT pid, usename, application_name, client_addr, state,
       now() - xact_start AS xact_age, now() - state_change AS state_age, left(query, 120) AS query
FROM pg_stat_activity WHERE pid = <pid>;
```

## Сессии

| Команда | Что делает | Последствия для RX | Откат |
|---|---|---|---|
| `SELECT pg_cancel_backend(<pid>);` | отменяет текущий запрос, сессия остаётся | операция пользователя или фонового процесса падает с `canceling statement due to user request`, транзакция откатывается | нет; операцию повторяют |
| `SELECT pg_terminate_backend(<pid>);` | закрывает сессию, её транзакция откатывается | сервис RX видит `57P01` и переподключается, текущая операция падает, фоновая уходит на повтор | нет; несохранённое в этой транзакции теряется |

Порядок для зависших `idle in transaction`: показать список, договориться о каждом pid, завершать по одному.

```sql
SELECT pid, usename, application_name, now() - state_change AS idle, left(query, 80) AS last_query
FROM pg_stat_activity
WHERE state LIKE 'idle in transaction%' AND now() - state_change > interval '30 minutes'
ORDER BY state_change;
```

Нельзя:

- завершать сессии RX массово (`pg_terminate_backend` по всем pid приложения): обрываются фоновые операции, которые потом начнутся сначала;
- трогать служебные процессы (`walsender`, `autovacuum`, `checkpointer`): autovacuum вернётся сам, остальные нужны базе;
- убивать процессы PostgreSQL через `kill -9`: сервер оборвёт все сессии и уйдёт в восстановление по журналу.

Подготовленная транзакция (2PC) снимается `ROLLBACK PREPARED '<gid>';` или фиксируется `COMMIT PREPARED '<gid>';`. Справка RX требует `max_prepared_transactions` равным `max_connections` (inst_podgotovka_k_ustanovke_linux.htm), то есть RX такими транзакциями пользуется. Решение о зависшей это решение о данных, а не об инфраструктуре: только с разработчиками или вендором.

## Слоты репликации

```sql
SELECT pg_drop_replication_slot('<имя слота>');
```

Необратимо. Реплика, которая пользовалась слотом, после этого может не догнать ведущий сервер, и её придётся пересоздавать с нуля. Перед удалением: слот неактивен (`active = false`), в `pg_stat_replication` нет реплики с этим слотом, владелец реплики подтвердил, что она не нужна. Слоты не удаляют списком.

Предел удержания WAL слотами (PostgreSQL 13 и новее) задаётся без перезапуска:

```sql
ALTER SYSTEM SET max_slot_wal_keep_size = '32GB';
SELECT pg_reload_conf();
```

Плата: отставшая сверх предела реплика станет недействительной и потребует пересоздания, зато ведущий сервер не упрётся в диск. Откат: `ALTER SYSTEM RESET max_slot_wal_keep_size; SELECT pg_reload_conf();`. Размер выбирают меньше свободного места на разделе `pg_wal`.

## Настройки

1. До изменения: `SELECT sourcefile, sourceline, name, error FROM pg_file_settings WHERE error IS NOT NULL;` пусто.
2. Изменение: строка в `postgresql.conf` (или в файле в `conf.d`) либо `ALTER SYSTEM SET <параметр> = <значение>;` (пишется в `postgresql.auto.conf`).
3. Применение: `SELECT pg_reload_conf();`, затем `SELECT name FROM pg_settings WHERE pending_restart;` покажет то, что ждёт перезапуска.
4. Откат: вернуть строку или `ALTER SYSTEM RESET <параметр>;`, снова `pg_reload_conf()`.

В кластере Patroni параметры, общие для всех узлов, меняются в общей конфигурации Patroni, а не в `postgresql.conf` (справка RX: admin_patroni_dcs_astralinux.htm и соседние статьи для РЕД ОС и Альт).

Перезапуск PostgreSQL обрывает все сессии: пользователи RX получат ошибки, в логах сервисов будут `57P01` и `57P03`, сервисы переподключатся сами. Только в окно обслуживания. Имя службы зависит от сборки, его сначала смотрят: `systemctl list-units 'postgresql*'`.

## Очистка и индексы

| Команда | Блокировка и нагрузка | Когда |
|---|---|---|
| `VACUUM (VERBOSE, ANALYZE) <таблица>;` | не мешает чтению и записи, нагружает диск | в спокойное время, если autovacuum не успевает |
| `VACUUM (FREEZE, VERBOSE) <таблица>;` | то же, читает всю таблицу | при угрозе wraparound, начиная со старейших таблиц |
| `ANALYZE <таблица>;` | лёгкая | после массовой загрузки, при плохих планах |
| `VACUUM FULL <таблица>;` | `AccessExclusiveLock`: таблица недоступна, нужно место под копию, много WAL | только в окно, после согласия |
| `CREATE INDEX CONCURRENTLY ...;` | без блокировки записи, дольше обычного | только после того, как план запроса показал, что индекс нужен |
| `REINDEX INDEX CONCURRENTLY <индекс>;` | без блокировки записи | раздутый или повреждённый индекс |

- Таблицы RX принадлежат прикладной разработке. Индекс, созданный руками, живёт до первого обновления и может с ним конфликтовать: его вносят в разработку, а до этого записывают в журнал изменений.
- Прерванный `CREATE INDEX CONCURRENTLY` оставляет индекс в состоянии INVALID. Его находят запросом `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;` и удаляют `DROP INDEX CONCURRENTLY <индекс>;`.
- Перестроения и `VACUUM FULL` порождают WAL в объёме таблицы: заранее проверьте место под `pg_wal` и под архив.

## Переполненный диск

- Файлы из `pg_wal` руками не удаляют никогда. Архив WAL на сервере копий тоже не чистят по дате: порядок для него в скиле `rx-backup-check`.
- Освободить место можно за счёт старых журналов сервера (`$PGDATA/log`, `/var/log/postgresql`), чужих файлов на томе или расширения тома. Удаление журналов тоже изменение: список файлов показывают пользователю.
- `archive_mode` не выключают и `archive_command` не очищают: точка восстановления уедет на последнюю полную копию, а при пустой команде сегменты продолжат копиться.

## Проверка команды архивации

Ошибку команды обычно видно в журнале PostgreSQL сразу после строки `archive command failed` (там же `DETAIL` с самой командой). Повторять команду руками в настоящий архив не надо: сегмент окажется в архиве, и команда вида `test ! -f <архив>/%f && cp %p <архив>/%f` начнёт падать уже на нём. Проверяйте по частям под пользователем `postgres`: каталог есть и доступен на запись (`sudo -u postgres test -w <каталог архива> && echo ok`), место есть (`df -h <каталог архива>`), сетевой ресурс смонтирован (`findmnt <каталог архива>`). Если сегмент уже лежит в архиве, сравните его с файлом в `pg_wal` (`cmp`): одинаковый файл значит, что команду надо научить принимать уже заархивированный сегмент, разный значит, что в архив пишет кто-то ещё.
