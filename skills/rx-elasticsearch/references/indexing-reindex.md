# Индексирование RX и переиндексация

По справке Directum RX 25.2 (статьи в скобках) и справочнику ошибок drxinfra.ru.

## Как документ попадает в поиск

1. Пользователь сохраняет документ, версию, задачу или выполняет задание.
2. Веб-сервер кладёт запрос в очередь RabbitMQ `directumrx_<exchange>_indexing_service`.
3. IndexingService забирает сообщение, для полнотекстового поиска берёт содержимое у сервиса хранилищ
   и отправляет данные в Elasticsearch (`ar_servis_indeksirovaniia.htm`).

Поэтому «поиск не работает» может значить сбой в очереди, в сервисе индексирования, в сервисе хранилищ
или в самом Elasticsearch, а при отдельном сервере ещё и в сети между ними. Индексируется только
последняя версия документа; версии больше 75 МБ и файлы без текста (MP3, AVI, JPEG, ZIP, PDF без
текстового слоя) попадают в поиск только карточкой (`admin_pervonachalnoe_indeksirovanie_linux.htm`).

Настройки сервиса индексирования (`admin_config_indexingservice_linux.htm`): `MAX_RETRIES_PROCESS_MESSAGE`
(после исчерпания попыток сообщение удаляется из очереди), `MAX_PARALLEL_MESSAGES_PROCESSING_COUNT`
(по умолчанию 25, от 1 до 25), `MAX_PARALLEL_INITIAL_BULK_MESSAGES_PROCESSING_COUNT` (по умолчанию 5).

## Что смотреть по порядку

1. **Очередь.** `mq_check.py` из скила `rx-rabbitmq`: сколько сообщений в `..._indexing_service`, есть ли
   потребители, убывает ли очередь между замерами. По справке растущая или застывшая очередь значит, что
   документы в Elasticsearch не поступают (`admin_indeksirovanie_dokumentov_linux.htm`).
2. **Проверки здоровья.** В статус-файлах сервиса индексирования (по умолчанию подпапка `status` рядом с
   логами, `STATUS_FILE_PATH`, `admin_obshchie_nastroiki_linux.htm`) смотрите `ELASTIC_SEARCH` и
   `INDEXING_SERVICE`. `INDEXING_SERVICE: degraded` значит 25 ошибок подряд: сервис перестал забирать
   очередь и вернётся сам, когда обработка наладится. Обычно причина в Elasticsearch: диск, блокировки,
   red, недоступность.
3. **Лог сервиса индексирования.** Ищите `IndexingServiceMessageHandler`, `Indexing completed with an error`
   и ответ Elasticsearch во внутреннем исключении:
   - 429 и `cluster_block_exception`: индекс закрыт на запись (`references/disk-blocks.md`);
   - 503, `all shards failed`, отказ соединения: кластер red или недоступен;
   - 400, `mapper_parsing_exception`, `document_parsing_exception`, immense term: документ не подошёл
     к схеме индекса (`references/heap-shards.md`); пример, поле и значение передать разработчикам;
   - `Entity update conflict for ... Message will be sent back to queue for reprocessing`: две операции
     одновременно обновили одну запись, сообщение вернулось в очередь; единичные записи не страшны;
   - не извлёкся текст: файл повреждён, зашифрован или формат не поддерживается; документ будет
     находиться только по карточке.
4. **Прирост документов.** `es_check.py --interval 300` или
   `curl -s -u <логин> "$ES_URL/_cat/indices/*rxsearch*?v&h=index,health,docs.count"` дважды. Справка
   предлагает то же через Kibana (Stack Monitoring, Docs Count). Документы в RX меняются, а здесь ноль:
   смотрите очередь и лог.

## Один документ не находится

Причины по справке (`admin_ustranenie_neispr_poiska_linux.htm`): нет прав у пользователя; последняя версия
без текста; версия больше 75 МБ; документа нет в индексе; мало критериев (Elasticsearch возвращает первые
10 000 результатов, и редкий документ может в них не попасть). Есть ли документ в индексе, проверяет
запрос только на чтение по ИД документа:

```bash
curl -s -u <логин> "$ES_URL/<префикс>rxsearch_document_<код системы>_<постфикс>/_search?q=entity_value_id:<ИД>&filter_path=hits.total,hits.hits._source.body.text.content_length"
```

`hits.total.value` 0: объект не проиндексирован, его индексируют по ИД (ниже). Больше 0, но нет
`body.text`: карточка в индексе, а текст не попал, причина в логе сервиса индексирования.

## Когда нужна переиндексация

- после переноса Elasticsearch на новый сервер, восстановления RX из резервной копии, переноса RX
  (`ar_servis_indeksirovaniia.htm`);
- после смены `ELASTICSEARCH_INDEX_PREFIX` или `ELASTICSEARCH_INDEX_POSTFIX` (`admin_obshchie_nastroiki_linux.htm`);
  поиск после смены смотрит в новые пустые индексы;
- после того как `ELASTICSEARCH_URL` был пуст: всё это время ничего не индексировалось;
- при ошибках схемы индекса (immense term и подобные) и при смене `number_of_shards`;
- после обновления RX, если об этом пишет справка новой версии (например, при обновлении с 4.7.40.0 и
  ниже для поиска по критериям, `inst_rx_47_410_linux.htm`).

Не нужна, если индексы закрылись из-за диска или кластер был red: после исправления Elasticsearch очередь
индексирования догонит сама.

## Как переиндексировать (изменение, только с согласия)

По справке (`admin_pervonachalnoe_indeksirovanie_linux.htm`), Linux, Directum Launcher:

- в конфигураторе добавить секции IndexingService и InitialIndexing и применить настройки;
- в режиме «Индексирование» отметить «Документы» и «Задачи и задания», при желании задать период;
- или из командной строки в папке Directum Launcher:
  ```bash
  ./do.sh indexing up
  ./do.sh initialindexing run --command="-w -d"                                   # всё
  ./do.sh initialindexing run --command="""01.01.2020"" ""01.01.2021"" -d -w"     # за период
  ./do.sh initialindexing run --command="-d -id="1265,3312""                      # документы по ИД
  ```
  Периоды идут без промежутков; по ИД одна команда на один тип объектов (`-d`, `-t`, `-a`).
- в Kubernetes и без Directum Launcher утилиту запускают в Docker (`admin_initialindexing_docker.htm`).

Ключ `-r` (`--reindex`) очищает очередь индексирования, удаляет созданные индексы и запускает
первоначальное индексирование заново. До конца перестройки поиск находит только то, что уже успело
проиндексироваться. Предлагайте его только когда очередь безнадёжно застряла или индексы испорчены, с
оценкой времени и в нерабочее время.

Регулярный контроль (`admin_kontrol_index_linux.htm`): фоновые процессы «Исправление ошибок индексации
документов» и «Исправление ошибок индексации задач, заданий и уведомлений» раз в сутки повторяют
индексацию объектов, по которым сервис оставил сообщения об ошибке в хранилище отложенных операций.
«Проверка индексации документов» и «Проверка индексации задач, заданий и уведомлений» по умолчанию
выключены: они проверяют все объекты и отправляют непроиндексированные, их запускают вручную при массовых
ошибках. Ручной запуск даёт нагрузку, это тоже изменение с согласия.

После работ: очередь `indexing_service` пустеет, `es_check.py --interval 300` показывает рост документов,
`INDEXING_SERVICE` и `ELASTIC_SEARCH` healthy, контрольный документ находится по тексту.
