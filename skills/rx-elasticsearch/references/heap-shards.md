# Куча JVM, предохранители, шарды, поля

Изменения (размер кучи, лимиты, настройки индексов) только с согласия и с откатом.

## Куча и память

Elasticsearch держит в куче служебные структуры индексов и результаты запросов, а сами данные читает
через файловый кэш системы. Отсюда правила калькулятора drxinfra (https://drxinfra.ru/elasticsearch-config.html):

- куча половина памяти, остальное файловому кэшу; не больше 31 ГБ, выше Java теряет сжатые указатели;
- `-Xms` равно `-Xmx`, иначе куча растёт на ходу и даёт паузы;
- в контейнере лимит памяти примерно вдвое больше кучи;
- `bootstrap.memory_lock: true` и memlock без ограничений, чтобы куча не ушла в подкачку;
- параметр ядра `vm.max_map_count = 262144` на сервере Elasticsearch: без него узел в рабочем режиме не
  стартует (так же в справке RX, `admin_install_es_dl.htm`).

Где задаётся куча, зависит от установки: у пакета файл в `/etc/elasticsearch/jvm.options.d/`, у
контейнера переменная `ES_JAVA_OPTS="-Xms4g -Xmx4g"`. Где её задаёт Directum Launcher для своего
контейнера, справка 25.2 не пишет: смотрите справку своей версии и конфигурацию на тестовом стенде.

```bash
curl -s -u <логин> "$ES_URL/_cat/nodes?v&h=name,heap.percent,heap.max,ram.percent,ram.max"
curl -s -u <логин> "$ES_URL/_nodes/stats/jvm,breaker?filter_path=nodes.*.name,nodes.*.jvm.mem.heap_used_percent,nodes.*.breakers.parent"
```

## Предохранители (circuit breakers)

Перед запросом узел оценивает, хватит ли памяти. Не хватит: запрос отклоняется с
`circuit_breaking_exception ... Data too large`, узел остаётся жив. Общий предохранитель `parent`
срабатывает около 95 % кучи. Поле `tripped` считает срабатывания с запуска узла. На стенде 7.17.23
сработавший предохранитель запроса выглядел так:
`[request] Data too large, data for [preallocate[aggregations]] would be [...], which is larger than the limit of [...]`.

Причины: куча мала для данных, слишком много шардов, тяжёлые агрегации, большие пакеты при индексации.
Лечение: больше кучи (в пределах правил выше), меньше шардов, для ошибок записи меньший размер пакета у
того, кто пишет.

`java.lang.OutOfMemoryError: Java heap space` и затем `fatal error in thread [...], exiting`: куча
кончилась совсем, процесс завершился. Журнал пакетной установки `/var/log/elasticsearch/*.log`, у
контейнера `docker logs <контейнер>`. Причины и лечение те же.

## Лимит шардов

У кластера предел `cluster.max_shards_per_node`, по умолчанию 1000 на узел данных; считаются открытые
шарды вместе с репликами. На пределе новый индекс не создаётся:
`this action would add [2] shards, but this cluster currently has [1000]/[1000] maximum normal shards open`.
Индексов RX немного, предел обычно съедают журналы в общем кластере: новые индексы каждые сутки без
удаления старых.

- Быстро вернуть запись (изменение, сразу): `PUT _cluster/settings {"persistent": {"cluster.max_shards_per_node": 1500}}`;
  откат тем же запросом со значением `null`. Без уборки так нельзя бесконечно: каждый шард держит память.
- Убрать причину: удалить старые индексы журналов, настроить срок хранения (ILM) и привязать политику и к
  уже созданным индексам, один шард на небольшой суточный индекс.
- Ориентир документации Elasticsearch 7.x: не больше 20 шардов на гигабайт кучи.

## Размер шарда индексов RX

Справка RX (`admin_nastroyka_indeksov_elasticsearch_linux.htm`): рекомендуемый размер индекса Lucene (шарда)
30 ГБ, документы при индексировании ужимаются минимум втрое, поэтому один шард на 90 ГБ документов.
Если документов больше, `number_of_shards` = объём документов в ГБ / 90 с округлением вверх, с запасом на
рост. Значение задаётся в `document_template.json` (для задач и заданий `workflow_template.json`) внутри
архива InitialIndexing в папке Directum Launcher, по умолчанию 1, и действует только для заново созданных
индексов, то есть с переиндексацией. `es_check.py` предупреждает, если основной шард индекса RX больше 30 ГБ.

## Лимит полей и immense term

- `Limit of total fields [1000] has been exceeded while adding new fields`: в индексе больше полей, чем
  `index.mapping.total_fields.limit` (по умолчанию 1000). Обычно это индексы журналов: у сообщений RX
  разные вложенные ключи в `args` и `cust`, и при автоматическом создании полей их число растёт. Быстро:
  поднять предел у индекса (изменение) и в шаблоне; правильно: хранить разнородные объекты одной строкой
  или выключить для них автоматическое создание полей. Если ошибка пришла на индекс `rxsearch_*`, это
  не типовой случай: соберите пример и передайте вендору.
- `Document contains at least one immense term in field="content" (whose UTF8 encoding is longer than the max length 32766)`:
  длинный текст попал в поле типа `keyword` (индекс создан без нужного шаблона или с неверным).
  Проверка: `GET <индекс>/_mapping/field/<поле>`. Тип существующего поля не меняется, повторная
  индексация в тот же индекс не поможет: индекс пересоздают с верной схемой, для RX штатной процедурой
  (`references/indexing-reindex.md`).
