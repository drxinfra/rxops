# Временные очереди и политика expires

## Откуда тысячи очередей

Калькулятор drxinfra описывает это так: сервисы RX при запуске объявляют служебные очереди с
уникальным идентификатором в имени, а после перезапуска сервиса старая очередь остаётся. За месяцы
их набираются тысячи. Каждая держит память и метаданные, в кластере ещё и время на согласование, и
брокер начинает тормозить без единой большой очереди. Политика `expires` на кластере сократила число
очередей с 3207 до 597 (замер drxinfra).

Но GUID в имени ещё не значит мусор. По справке RX (`monitoring_sostoyanie_rabbitmq.htm`) очередь с
GUID может принадлежать фоновому процессу (GUID совпадает с полем JobId таблицы Sungero_Core_Job) или
асинхронному обработчику (проверяется в среде разработки).

## Как отличить

1. `mq_check.py` группирует очереди по форме имени (GUID и хеш заменены на `<guid>` и `<hex>`). Признак
   очередей экземпляров: серия однотипных очередей, у которых потребитель есть у одной или у нескольких
   (по числу живых экземпляров сервиса), а остальные пустые и без потребителей.
2. Одиночная очередь с GUID похожа скорее на очередь фонового процесса или обработчика. Сверьте GUID с
   базой, запрос только читает (имена таблицы и поля по справке, на своей версии проверьте):
   ```sql
   select * from sungero_core_job where jobid = '<GUID из имени очереди>';
   ```
   Нашлась строка: это очередь фонового процесса, под политику её не включают.
3. Проверьте шаблон на живом списке, ничего не меняя:
   ```bash
   python3 ${CLAUDE_SKILL_DIR}/scripts/mq_check.py --vhost <vhost> --match '<шаблон>'
   ```
   Шаблон хорош, если под него попадают только серии однотипных очередей, без очередей без GUID,
   без одиночных GUID и без очередей с сообщениями. Предупреждения скрипта разберите все.

## Политика (изменение, только с согласия)

Так её предлагает калькулятор drxinfra: очередь по шаблону, которой сутки никто не пользуется,
удаляется сама.

```bash
rabbitmqctl set_policy -p <vhost> rx-orphan-expire '<шаблон, проверенный через --match>' \
  '{"expires":86400000}' --apply-to queues --priority 1
```

Что объяснить пользователю до согласия. Всё ниже проверено на тестовом брокере 3.13.7:

- **К очереди применяется одна политика**, с наибольшим приоритетом (документация RabbitMQ, Policies).
  После команды выше очереди по шаблону перестали подчиняться политике `ha-all` и перешли на новую.
  Если на брокере есть политика зеркалирования (так кластер настраивает справка RX 25.2,
  `admin_cluster_rmq.htm`) или политики Ario с `consumer-timeout`, их ключи нужно повторить в
  определении новой политики, например `'{"expires":86400000,"ha-mode":"all","ha-sync-mode":"automatic"}'`,
  иначе подходящие очереди потеряют зеркалирование или таймаут.
- **Очередь удаляется вместе с сообщениями.** «Не используется» значит: нет потребителей, её не
  объявляли заново и из неё не читали `basic.get` дольше срока (документация RabbitMQ, TTL). На тесте
  очередь без потребителя с тремя сообщениями удалилась вместе с ними, а очередь с живым потребителем
  осталась. Значит, если сервис простоит дольше срока (выходные, долгие работы), его очереди под
  шаблоном исчезнут с содержимым. Срок берите заметно больше самого долгого планового простоя.
- **Кворумные очереди** поддерживают `expires` частично: срок не продлевается повторным объявлением
  очереди (документация RabbitMQ, Quorum Queues).
- Удаление не мгновенное: брокер удаляет очередь после срока, но без гарантии, насколько быстро.

Проверка после: через срок `mq_check.py` показывает меньше очередей без потребителей, живые очереди
сервисов на месте, ошибок подключения в логах RX нет. Откат политики:
`rabbitmqctl clear_policy -p <vhost> rx-orphan-expire`. Удалённые очереди откат не вернёт: сервисы
объявляют свои очереди при запуске, а сообщения в удалённых очередях потеряны.

## Ручное удаление вместо политики

Только по списку, согласованному с пользователем, и только пустых очередей без потребителей:
`rabbitmqctl delete_queue --vhost <vhost> <имя> --if-empty --if-unused`. Ключи `--if-empty --if-unused` не
дают удалить очередь с сообщениями или с потребителем. Отката нет.
