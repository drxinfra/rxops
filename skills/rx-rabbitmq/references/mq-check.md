# mq_check.py: запуск, учётка, пороги

Скрипт только читает: к API управления ходит одними GET-запросами, из rabbitmqctl вызывает только
`list_*`, `status` и `cluster_status`. Ничего не создаёт, не удаляет и не меняет.

## Откуда берёт данные

| Режим | Как запустить | Что видно |
|---|---|---|
| API управления (по умолчанию) | `RABBITMQ_URL=http://mq01:15672 RABBITMQ_USER=monitor python3 mq_check.py` | всё: узлы, тревоги, очереди, потребители, соединения, политики |
| rabbitmqctl на сервере брокера | `python3 mq_check.py --ctl` | то же, но память, диск и дескрипторы только того узла, где запущено |
| брокер в контейнере | `python3 mq_check.py --ctl --ctl-prefix "docker exec rabbitmq"` | как `--ctl`; для Kubernetes префикс `"kubectl exec -n <ns> <pod> --"` |
| готовый вывод | `rabbitmqctl list_queues -p <vhost> name messages messages_ready messages_unacknowledged consumers \| python3 mq_check.py --stdin --vhost <vhost>` | только очереди; понимает таблицу, `--formatter json` и сохранённый ответ `/api/queues` |

Пароль берётся из `RABBITMQ_PASSWORD` или из файла в формате netrc (`--netrc ФАЙЛ`, строка
`machine mq01 login monitor password ...`, права 600). В вывод пароль не попадает, адрес печатается
без имени и пароля. Для https: `--cacert ФАЙЛ` (или `RABBITMQ_CA`); `--insecure` отключает проверку
сертификата и пишет об этом в заголовке, используйте только осознанно.

Файл netrc пользователь заполняет сам, агент его не читает и пароль не видит. Переменную `RABBITMQ_PASSWORD` можно задать в своём терминале до запуска агента. `read -s` внутри команды агента не работает: его командный инструмент не интерактивный.

## Ключи

- `--vhost V` только один vhost.
- `--interval N` второй замер через N секунд: рост очередей, неподтверждённые, которые не двигаются,
  шторм подключений. Берите 60 секунд и больше, иначе медленный рост не заметен.
- `--json > before.json`, потом `--compare before.json`: сравнение с сохранённым замером, например до и
  после работ.
- `--match 'РЕГВЫР'` какие очереди попадут под шаблон политики, с предупреждениями (рабочие очереди под
  шаблоном, очереди с сообщениями, одиночные GUID, уже действующие политики). Шаблон проверяется по
  правилам Python; простые выражения RabbitMQ понимает так же, сложные проверьте на тестовом стенде.
- `--expect-tls` считать отклонением клиентов без TLS (во время перехода на TLS).
- `--warn-messages 5000`, `--crit-messages 50000`, `--warn-temp 1000`, `--growth-min 100` пороги.
  50 тысяч взяты из чек-листа вендора, остальное стартовые значения: подберите по своему фону.

## Проверки

| Проверка | CRIT | WARN |
|---|---|---|
| `alarms` | тревога по памяти или диску | |
| `memory` | | память от 80 % порога |
| `disk` | | свободно меньше двух порогов; порог меньше 2 ГБ |
| `fd`, `limits` | дескрипторы от 95 % | от 80 %; лимит меньше 65536; сокеты и процессы от 80 % |
| `nodes` | узел не работает; разделение сети | |
| `queue_state` | очередь down, crashed, minority и подобные | |
| `no_consumers` | у очереди без GUID в имени есть сообщения и нет потребителей | |
| `backlog` | от 50 тысяч сообщений | от 5 тысяч при живых потребителях |
| `unacked` | | много неподтверждённых; при двух замерах не двигаются |
| `growth` | растёт очередь без потребителей | растёт очередь с потребителями |
| `temp_queues` | | от 1000 очередей с GUID или хешем без потребителей; одиночная очередь с GUID с сообщениями и без потребителей; от 5 тысяч сообщений в таких очередях |
| `quorum` | нет большинства копий или лидера | часть копий недоступна |
| `policies` | | ha-mode на RabbitMQ 4.x |
| `connections` | соединения blocked | flow, тысяча каналов на соединение, шторм подключений |
| `users`, `tls` | | есть guest; клиенты без TLS при `--expect-tls` |
| `access` | | у учётки нет прав на vhost, где есть сообщения |

Строки INFO не влияют на итог: версия, самые большие очереди, группы временных очередей, соединения
по пользователям и адресам, политики, заметки о том, что прочитать не удалось.

Код возврата: 0 норма, 1 найдено отклонение, 2 не удалось проверить (нет связи, нет прав, пустой ввод).

## Учётка только на чтение

Изменение на брокере, только с согласия. Так её заводит калькулятор drxinfra:

```bash
rabbitmqctl add_user monitor '<пароль>'
rabbitmqctl set_user_tags monitor monitoring
rabbitmqctl set_permissions -p <vhost> monitor "^$" "^$" "^$"
```

Права `"^$"` запрещают публиковать и читать сообщения, но дают видеть vhost. Проверено на 3.13.7:
учётка с тегом monitoring без прав на vhost его очередей не видит (API отвечает «not_authorised»),
поэтому права выдают на каждый vhost, включая vhost сервисов Ario. Откат: `rabbitmqctl delete_user monitor`.
Список пользователей (проверка guest) учётке monitoring недоступен, это нормально.

## Что учесть при чтении

- Счётчики в API обновляются раз в несколько секунд. На тестовом брокере сразу после публикации API ещё
  показывал пустую очередь, а флаги тревоги в `/api/nodes` появились секунд через десять. Поэтому
  тревоги скрипт берёт из `/api/health/checks/alarms`, а цифры очередей при сомнении перепроверьте
  через `--ctl` или второй замер.
- Короткие соединения, которые открываются и сразу закрываются, в списке соединений не видны. Шторм
  виден только при двух замерах по счётчику новых соединений, а кто его устраивает, показывает журнал
  брокера (`references/client-errors.md`).
- Если опрашивать кластер через общий адрес, каждый запрос попадает на случайный узел. Для регулярного
  мониторинга опрашивайте узлы по отдельности.
