# Пороги памяти и диска, лимиты, consumer_timeout, guest

Все команды, которые меняют настройки брокера, показываются пользователю с объяснением и откатом и
выполняются только после согласия. Числа ниже из калькулятора drxinfra
(https://drxinfra.ru/rabbitmq-config.html) и документации RabbitMQ.

## Тревога по памяти

Брокер дошёл до `vm_memory_high_watermark` и блокирует публикацию, пока память не освободится.
По умолчанию порог 40 % видимой памяти в 3.13 и 60 % в 4.x (на тестовых брокерах 3.13.7 и 4.4.0 так и
есть). Память растёт, когда сообщения копятся быстрее, чем их разбирают, или когда очередей и
соединений тысячи.

```bash
rabbitmq-diagnostics memory_breakdown
rabbitmqctl list_queues -p <vhost> name messages consumers | sort -k2 -n | tail
rabbitmq-diagnostics status | grep -i -A2 memory
```

Лечится разбором очереди (поднять её обработчик), а не порогом. Ловушка контейнера: по замеру drxinfra
RabbitMQ 3.13 в Docker посчитал порог от памяти сервера, 7 ГБ при лимите контейнера 400 МБ. Тревога в
такой конфигурации не сработает: контейнер убьют по памяти раньше. Сравните «порог» в выводе
`mq_check.py` с лимитом контейнера (`docker inspect -f '{{.HostConfig.Memory}}' <контейнер>`). Исправление
(изменение, с перезапуском узла): в rabbitmq.conf задать порог явно, например
`vm_memory_high_watermark.absolute = 1GB` (примерно 60 % лимита контейнера) или
`total_memory_available_override_value` с реальным объёмом. Сразу и до перезапуска действует
`rabbitmqctl set_vm_memory_high_watermark absolute "1GB"`. Откат: вернуть прежнюю строку и значение.

## Тревога по диску

Свободного места меньше `disk_free_limit`: публикация заблокирована, чтение идёт. По умолчанию порог
50 МБ (проверено на 3.13.7 и 4.4.0: 50000000 байт), это слишком поздно. Калькулятор drxinfra ставит
порог в полтора порога памяти и не меньше 2 ГБ, а том под данные брокера в несколько раз больше порога.

```bash
rabbitmq-diagnostics status | grep -i -A3 -E 'free disk|data directory'
df -h /var/lib/rabbitmq
```

В выводе status строки `Low free disk space watermark` (порог) и `Free disk space`, а в разделе
`Data directory` путь к данным узла: на него и смотрите `df` и `du`.

Порядок: освободить место или расширить том, найти, что его заняло (накопленные очереди, журналы
брокера). Тревога снимается сама, как только свободного станет больше порога. Отдельная ловушка: том
меньше или равен порогу. Тогда тревога не снимется никогда, даже на пустом диске. Порог в этом случае
неверный, и его меняют вместе с размером тома:

```bash
rabbitmqctl set_disk_free_limit "2GB"      # сразу, до перезапуска
# и в rabbitmq.conf, чтобы пережило перезапуск:
disk_free_limit.absolute = 2GB
```

Откат: прежнее значение той же командой и в файле.

## Дескрипторы и процессы

Каждое соединение занимает файловый дескриптор. Документация RabbitMQ требует лимит не меньше 65536,
у службы по умолчанию бывает 1024. У службы systemd это `LimitNOFILE` в `systemctl edit rabbitmq-server`
(файл limits.conf на службы не действует), у контейнера ключ `--ulimit nofile=65536:65536`. Изменение
требует перезапуска узла. Если дескрипторы растут без роста числа клиентов, ищите утечку соединений
(`mq_check.py --interval 60`, раздел «Соединения»).

## consumer_timeout

С RabbitMQ 3.8.15 брокер ждёт подтверждения сообщения не дольше `consumer_timeout`, по умолчанию
30 минут. Дольше: канал закрывается с `PRECONDITION_FAILED` (406), сообщение возвращается в очередь,
сервис берёт его снова. Для пользователя это «висит и не завершается».

На тестовом брокере 3.13.7 потребитель, который взял сообщения и не подтверждал их, через 30 минут
получил в журнале брокера предупреждение `Consumer '...' on channel 1 and queue '<очередь>' in vhost
'<vhost>' has timed out waiting for a consumer acknowledgement ... Timeout used: 1800000 ms` и ошибку
`operation none caused a channel exception precondition_failed: delivery acknowledgement on channel 1
timed out`. Клиент не переподключился, и очередь осталась без потребителя: так выглядит сервис, который
после этой ошибки не восстановил подписку.

- Значение у потребителей `mq_check.py --interval 60` показывает в строке о неподтверждённых
  сообщениях (поле `consumer_timeout` в `/api/consumers`, проверено на 3.13.7). Через CLI:
  `rabbitmqctl eval 'application:get_env(rabbit, consumer_timeout).'` (выражение только читает).
- Сначала ищут, почему обработчик идёт дольше получаса: тяжёлый запрос, большой документ, ожидание
  внешней системы. Это фактура для разработчиков.
- Если долгая обработка ожидаема, таймаут увеличивают в rabbitmq.conf, в миллисекундах:
  `consumer_timeout = 7200000`, с перезапуском узла. Совсем не отключают: зависший обработчик будет
  держать сообщения бесконечно.
- Сервисы Directum Ario на отдельном брокере требуют своих политик с `consumer-timeout` для очередей
  извлечения текста и обучения (справка `arioinstall_linux_rabbitmq.htm`). К очереди применяется одна
  политика: новая политика с большим приоритетом над этими очередями отменит их таймауты.

## Пользователь guest

Справка RX советует после создания своего администратора удалить guest
(`admin_rabbitmq_linux_setting.htm`). Его пароль знают все. По умолчанию RabbitMQ пускает guest только с
localhost (`loopback_users.guest`), но в официальном образе Docker это ограничение снято: тестовый
брокер 3.13 принял guest:guest по сети. Перед удалением убедитесь, что под guest никто не подключён
(`mq_check.py`, раздел соединений), иначе этот клиент потеряет брокер. Удаление: `rabbitmqctl delete_user guest`,
откат: `rabbitmqctl add_user guest '<пароль>'` и права заново.
