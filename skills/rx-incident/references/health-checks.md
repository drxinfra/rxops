# Проверки работоспособности сервисов Directum RX

Пересказ справки Directum RX 25.2: «Проверка работоспособности сервисов»
(`admin_service_health_check_linux.htm`), «Общие проверки работоспособности»
(`admin_general_health_checks_linux.htm`), «Статус-файлы и лог-файлы»
(`admin_status_files_and_log_files_linux.htm`), «Управление памятью docker-контейнеров»
(`admin_upravlenie_docker_pamyatyu.htm`), «Настройка HAProxy» (`admin_nastroikahaproxy.htm`).
Пороги и состав проверок зависят от версии: сверяйтесь со справкой своей версии.

## Где смотреть статус

- Directum Launcher, режим «Состояние»: процессор, память и общий статус каждого сервиса, данные
  обновляются каждые 10 секунд, по щелчку на статусе открывается статус-файл.
- Командой из папки Directum Launcher: `./do.sh all check` или `./do.sh <сервис> check`.
- Статус-файлы `<компьютер>.<сервис>.status` в подпапке `status` папки журналов. Перезаписываются
  каждые 10 секунд, у каждого экземпляра сервиса свой файл. Если сервис не работает, файл
  не обновляется.
- Журналы сервисов: смена статуса любой проверки и раз в 30 минут текущее состояние всех проверок,
  искать по слову `health`.
- Решение «Мониторинг Directum RX», если оно установлено.

## Статусы

- `healthy`: все проверки прошли.
- `degraded`: хотя бы одна проверка нашла проблему, сервис продолжает работать.
- `unhealthy`: хотя бы одна проверка нашла критичную ошибку, сервис неработоспособен.

В статус-файле: `Time` время записи, `LastNotUnhealthyTime` когда общий статус последний раз был
не `unhealthy`, `Status` общий статус, `IsReady` готов ли принимать запросы, `Statuses` проверки,
у каждой `Status`, `Duration` и у некоторых `Data`. Разница между `Time` и `LastNotUnhealthyTime`
значит, что сервис всё это время неработоспособен.

## Общие проверки и пороги по умолчанию

| Проверка | Что проверяет | Когда не в порядке |
|---|---|---|
| `PROCESS_MEMORY` | память процесса сервиса | `degraded` выше `degradedValue`, `unhealthy` выше `value` (МБ, у каждого сервиса свои) |
| `QUEUE` | работу с RabbitMQ | `degraded` дольше 2000 мс, `unhealthy` при ошибке или дольше 5000 мс |
| `THREAD_POOL` | свободные рабочие потоки | `degraded` меньше 15 %, `unhealthy` меньше 7 % свободных |
| `CERTS_EXPIRATION` | сроки сертификатов, которые сервис загрузил при старте | `degraded` за 14 дней до окончания, `unhealthy` срок истёк |
| `DATABASE` | подключение и простой запрос к базе | `degraded` дольше 8 с, `unhealthy` при ошибке или тайм-ауте 18000 мс |
| `CRITICAL_EXCEPTION` | критичные необработанные исключения, кэш чистится раз в 5 минут | `unhealthy`, если такие были |
| `WRITE_ACCESS_TO_FILE` | запись в рабочую папку сервиса и место на диске, раз в 120 с | `unhealthy`, если записать нельзя |
| `SERVER_START` | загрузился ли сервер | `unhealthy`, если нет |
| `MODULES_LOAD` | загрузились ли прикладные модули | `unhealthy`, если нет; `degraded` в безопасном режиме |

Пороги `PROCESS_MEMORY` по умолчанию в справке 25.2 (degraded / unhealthy, МБ): веб-сервер 4608 / 6144,
общий сервис, предпросмотр, блоки схем задач, асинхронные события, виджеты, отчёты, индексирование
4096 / 6144, интеграция 4608 / 6144, NOMAD 7168 / 8192, остальные сервисы 768 / 1024.

Лимит памяти docker-контейнера сервиса считается от этой проверки: `value` умножить на 1,5 (параметр
`LimitFactor` секции `MEMORY_LIMITS`), для сервисов с изолированной областью плюс
`ISOLATED_HOST_MAX_MEMORY_SIZE`. Swap в контейнере по умолчанию выключен. При превышении лимита
контейнер перезапускается. Если сервис перезапускается под нагрузкой, сравните его память
с этим лимитом, прежде чем искать утечку.

## Уникальные проверки сервисов

Статья справки «Уникальные проверки для сервисов» (`admin_unikalnyye_proverki_dlya_servisov_linux.htm`).
По имени проверки сразу видно, какая зависимость подвела.

| Проверка | Сервис | Когда не в порядке |
|---|---|---|
| `PREVIEW_STORAGE` | предпросмотр | `degraded`: сервис хранения предпросмотра не ответил или ответил дольше 5000 мс |
| `QUEUE_MESSAGE_PROCESSING` | асинхронные события | `degraded`: зависших сообщений фоновых процессов или асинхронных обработчиков не меньше, чем их можно обрабатывать параллельно (`JOBS_PROCESSING_PARALLEL_COUNT`, `ASYNC_HANDLERS_PROCESSING_PARALLEL_COUNT`); `unhealthy`: предел достигнут у обоих |
| `S3_SERVICE_ACCESS` | хранилища | недоступен сервис хранилищ или бакет объектного хранилища с содержимым, проверка раз в 120 с |
| `ORLEANS_RUNTIME` | виджеты | ошибка среды выполнения или недоступные узлы кластера сервиса виджетов |
| `ELASTIC_SEARCH` | индексирование | `unhealthy`: ошибка или нет соединения с Elasticsearch; `degraded`: ответ дольше 2000 мс; не выполняется без `ELASTICSEARCH_URL` |
| `INDEXING_SERVICE` | индексирование | `degraded`: 25 и больше ошибок обработки подряд, сервис перестал отслеживать очередь индексирования, пока обработка не наладится |
| `CENTRIFUGO` | клиентские подключения | `degraded`: Centrifugo отвечает дольше 500 мс; `unhealthy`: не отвечает или дольше 5000 мс |
| `NOMAD_HEALTH_CHECK` | NOMAD | `unhealthy`: ошибка или дольше 5000 мс |

Если сервис асинхронных событий или виджетов входит в общий сервис, его проверки настраиваются
в секции общего сервиса. Разборы в справочнике ошибок:
https://drxinfra.ru/errors/rx-healthcheck-degraded-statuses.html и
https://drxinfra.ru/errors/rx-health-check-result-has-been-changed.html.

## Адреса проверок для балансировщика

Пример настройки HAProxy в справке проверяет экземпляры по адресам `/client/api/health` (веб-сервер),
`/client/health` (хост веб-клиента), `/keyderivation/health`, `/log/health`, `/integration/health`,
`/preview/health`, `/storage/health`. Там же сказано, что для систем, обновлённых с ранних версий,
`Client` в пути заменяют на `drxweb`. Справка советует закрывать адрес `/Client/api/health`
для внешней сети на прокси. Балансировщик исключает экземпляр из работы, пока его проверка
сообщает о критичной ошибке. Формат ответа зависит от версии: смотрите на код ответа и время,
подробности в статус-файле.

```bash
curl -sk -o /dev/null -w '%{http_code} %{time_total}s\n' https://<адрес RX>/client/api/health
```
