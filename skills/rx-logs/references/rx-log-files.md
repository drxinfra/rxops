# Журналы Directum RX: файлы, поля, трасса

Пересказ справки Directum RX 25.2. Статьи: «Расположение лог-файлов» (`admin_logs_linux.htm`,
для Windows `admin_raspolozhenie_log_faylov.htm`), «Структура лог-файлов»
(`admin_struktura_log_failov_linux.htm`), «Трассировка в лог-файлах»
(`admin_trassirovka_log_fail_linux.htm`), «Лог-файлы во время работы»
(`admin_log_faily_vo_vremia_raboty_linux.htm`), «Статус-файлы и лог-файлы»
(`admin_status_files_and_log_files_linux.htm`). В других версиях имена могут отличаться:
сверяйтесь со справкой своей версии через rxmcp.

## Где лежат

Папка задаётся параметром `LOGS_PATH` в `config.yml` Directum Launcher. По умолчанию это
`<папка с данными>/logs` на Linux и `<папка с данными>\logs` на Windows. Справка советует держать
журналы на отдельном диске: если он переполнится, RX перестанет писать журналы, а система
и программы не пострадают.

## Серверные журналы

На Linux в имени есть имя компьютера и контейнера, на Windows только имя компьютера.
`<дата>` в виде `2026-10-22`.

| Компонент | Файл на Linux |
|---|---|
| Веб-сервер | `<компьютер>-<контейнер>.WebServer.<дата>.log` |
| Хост-приложение веб-сервера | `<компьютер>-<контейнер>.Client.Host.<дата>.log` |
| Кэширование данных (если включено) | `<компьютер>-<контейнер>.CacheManager.w3wp.<дата>.log` |
| Общий сервис | `<компьютер>-<контейнер>.GenericService.<дата>.log` |
| Сервис хранилищ | `<компьютер>-<контейнер>.StorageService.<дата>.log` |
| Сервис Workflow | `<компьютер>-<контейнер>.WorkflowProcessService.<дата>.log` |
| Выполнение блоков схем задач | `<компьютер>-<контейнер>.WorkflowBlockService.<дата>.log` |
| Отложенные операции | `<компьютер>-<контейнер>.Sungero.DelayedOperationsService.<дата>.log` |
| Асинхронные события | `<компьютер>-<контейнер>.Worker.<дата>.log` |
| Планировщик | `<компьютер>-<контейнер>.Sungero.JobScheduler.<дата>.log` |
| Предпросмотр | `<компьютер>-<контейнер>.PreviewService.<дата>.log` |
| Хранение файлов предпросмотра | `<компьютер>-<контейнер>.PreviewStorage.<дата>.log` |
| Индексирование | `<компьютер>-<контейнер>.IndexingService.<дата>.log` |
| Интеграция | `<компьютер>-<контейнер>.IntegrationService.<дата>.log` |
| Логирование | `<компьютер>-<контейнер>.LogService.<дата>.log` |
| Сервис ключей | `<компьютер>.KeyDerivationService.<дата>.log` |
| Публикация разработки | `<компьютер>.DeploymentToolCore.<дата>.log` |
| Утилита RxCmd | `<компьютер>.rxcmd.<дата>.log` |
| Сервис NOMAD | `server.<дата>.log` |
| Служба ввода документов | `<компьютер>.CaptureService.<дата>.log` |

Отличия Windows по справке:

- есть журнал агента ServiceRunner: `<компьютер>.Sungero.ServiceRunner.Host.<дата>.log`;
- если сервис блоков схем, асинхронных событий, отчётов или виджетов развёрнут в составе общего
  сервиса, его записи идут в `GenericService`, иначе в свой файл (`WorkflowBlockService`, `Worker`,
  `ReportService`, `WidgetsService`);
- сервис изолированного кода пишет `<имя сервиса>.IsolatedArea.<дата>.log`;
- сервис отложенных операций и планировщик пишутся без префикса `Sungero.`: `DelayedOperationsService`,
  `JobScheduler`.

## Клиентские и прочие журналы

- Веб-клиент и веб-агент: подпапка `remote` в папке серверных журналов, файлы
  `<IP компьютера>.WebClient.<код системы>.<ИД учётной записи>.<дата>.log` и
  `<IP компьютера>.WebAccessAgent.<код системы>.<ИД учётной записи>.<дата>.log`. Пишет их сервис
  логирования. Сообщения копятся и уходят порциями, по умолчанию по 100, выход пользователя
  отправляется сразу. Путь меняется параметром `LOGS_REMOTE_PATH` сервиса логирования, в нём
  можно использовать `${logs-path}`.
- Терминальная служба веб-агента: `proxy.log`, на Linux в `/var/log/webaccessagent`, на Windows
  в `%COMMONPROGRAMFILES%\WebAccessAgentSvc\Logs`.
- Directum Launcher: папка `DirectumLauncher/log`. `current.log` текущие сообщения, `all.log`
  прошлые, `dl.log` обновление, `DBConverter.log` конвертация базы при обновлении.
- Статус-файлы проверок работоспособности: подпапка `status`, `<компьютер>.<сервис>.status`,
  JSON, обновляются каждые 10 секунд. Если сервис не работает, файл не обновляется. Общий статус
  `healthy`, `degraded` или `unhealthy`, по каждой проверке свой статус и длительность. Разница между
  `Time` и `LastNotUnhealthyTime` значит, что сервис всё это время неработоспособен.
- Мобильные приложения Solo и Jazz: `log.txt` на устройстве, на сервер приходят в папку из
  `CLIENT_LOGS_PATH` сервиса NOMAD.

## Поля записи

Одна запись на строку, каждая запись объект JSON. Состав полей зависит от приложения.

| Поле | Что в нём |
|---|---|
| `t` | дата и время с часовым поясом: `2026-10-22 10:15:03.412+03:00` |
| `l` | уровень |
| `lg` | имя логгера, то есть компонента, который написал запись |
| `mt` | шаблон сообщения, строка или объект; параметры в `{...}` подставляются из `args` |
| `args` | параметры шаблона |
| `cust` | дополнительные сведения об объекте или свойстве |
| `ex` | исключение: `type` тип, `m` сообщение, `stack` стек, бывают и другие поля |
| `span` | длительность действия: название, начало, статус, `durationMs` |
| `tr` | трасса |
| `un` | учётная запись: `<домен>\<имя>` или `<имя>` |
| `v` | версия приложения или сервиса |
| `tn` | код системы |
| `tab`, `bn`, `bv` | вкладка браузера, название и версия браузера (журналы веб-клиента) |

В примерах справки встречается и поле `pid`. Журнал NOMAD добавляет `application`, `userAgent`,
`requestNumber`, `requestUrl`, `ip`, `hostName`, `nomadVersion`.

Две особенности, на которых ломаются инструменты: `mt`, `args` и `cust` в разных записях бывают
разного типа (строка или объект), а веб-агент пишет пути Windows с одиночным обратным слешем,
и такая строка не разбирается как JSON (статья drxinfra.ru про Vector).

## Уровни

`Fatal` прерывает работу приложения, `Error` прерывает операцию, `Warning` предупреждение без
прерывания (в журналах веб-клиента встречается `Warn`), `Info` значимые действия пользователя
и приложения, `Debug` и `Trace` отладка.

## Трасса

Поле `tr` связывает записи одного действия во всех сервисах. Вид: `<TraceId>-<RequestId>` для
HTTP-запроса или `<TraceId>-<MessageId>` для сообщения RabbitMQ, например `cl-4e326a73-7815ae`.
`TraceId` длиной 8 символов начинается с префикса сервиса, где началось действие. `RequestId`
6 символов, `MessageId` 10, у них тоже бывает префикс сервиса, который начал запрос или сообщение
(`ss3c75` от сервиса хранилищ, `dob78eac40` от отложенных операций). Только латинские буквы и цифры.

| Префикс | Сервис или приложение |
|---|---|
| `cc` | сервис клиентских подключений (ClientsConnectionService) |
| `ch` | SungeroClient.Host |
| `cl` | веб-клиент |
| `do` | отложенные операции (DelayedOperationsService) |
| `dt` | Deployment Tool Core |
| `gs` | общий сервис (GenericService) |
| `it` | интеграция (IntegrationService) |
| `ix` | индексирование (IndexingService) |
| `js` | планировщик (JobScheduler) |
| `kd` | сервис ключей (KeyDerivationService) |
| `lg` | логирование (LogService) |
| `pa` | Public API (SungeroPublicApi) |
| `ps` | хранение файлов предпросмотра (PreviewStorage) |
| `pv` | предпросмотр (PreviewService) |
| `rp` | отчёты (ReportService) |
| `ss` | хранилища (StorageService) |
| `wa` | веб-агент |
| `wb` | выполнение блоков схемы задачи (WorkflowBlockService) |
| `wi` | виджеты (SungeroWidgets) |
| `wk` | асинхронные события (SungeroWorker) |
| `wp` | Workflow (WorkflowProcessService) |
| `ws` | веб-сервер (SungeroWebServer) |

## Проверки работоспособности в журналах

Каждый сервис пишет в журнал смену статуса проверки (healthy, degraded, unhealthy и обратно)
и раз в 30 минут текущее состояние всех проверок. Ищутся по слову `health`. Запись
«Health check result has been changed.» сама по себе не авария: важно, какая проверка и как долго
(разбор: https://drxinfra.ru/errors/rx-health-check-result-has-been-changed.html).

## Журналы Docker

Directum Launcher создаёт контейнеры со своим ограничением журналов: до 5 файлов по 256 МБ на контейнер
в `/var/lib/docker/containers/<id>/`. Переменная `use_system_docker_log_settings: true` в `config.yml`
отключает это ограничение, и тогда действуют настройки Docker из `/etc/docker/daemon.json`
(по умолчанию без ротации). Журнал контейнера смотрят командой `docker logs`.

## Kubernetes

По справке сбор журналов RX в Kubernetes идёт из вывода контейнеров (источник `kubernetes_logs`
у Vector), поды RX помечены меткой `app: rx` (статья `monitoring_vector_kubernetes.htm`).
Пространство имён задают при установке, узнайте его у пользователя или через
`kubectl get pods -A -l app=rx`.

## Очистка журналов

Команда меняет систему, запускает её администратор, а не агент. По справке очистку ставят
в планировщик ОС:

```bash
./do.sh clean_logs --config_path="<путь до config.yml>" --skip_last_modified_days="7"
```

Без ключей берётся `config.yml` в папке Directum Launcher и остаются файлы за последние 7 дней.
Значение `0` удаляет все журналы. Перед очисткой посмотрите, нет ли среди старых файлов тех, что нужны
для разбора текущего случая.
