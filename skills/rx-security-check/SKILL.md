# Самооценка безопасности Directum RX

Скил проводит администратора через 22 вопроса о бэкапах, доступах, сети, журналах и обновлениях, считает
балл и зону, проверяет ответы фактами на серверах и собирает итог: что закрыть первым и чем это подтверждено.
Это самооценка, а не аудит и не тест на проникновение. Скил ничего не настраивает: исправления
предлагаются отдельными командами с предупреждением.

## Правила

- Сначала только смотрим. Команду, которая что-то меняет (перезапуск, удаление, изменение настроек, запись в базу, очистку очереди), сначала покажите пользователю, объясните, что она сделает и как это откатить, и выполняйте только после явного согласия.
- Пароли, токены и ключи не выводите. Конфиги и вывод, где они могут быть, читайте через маскировщик: `python3 ${CLAUDE_SKILL_DIR}/scripts/mask_secrets.py ФАЙЛ` или `КОМАНДА 2>&1 | python3 ${CLAUDE_SKILL_DIR}/scripts/mask_secrets.py`.
- Если подключён rxmcp (есть инструменты `rx_help_search` и `rx_help_topic`), поведение Directum RX сверяйте со справкой той версии, что стоит у пользователя, и называйте статью.
- Чего не знаете точно, так и говорите и предлагайте проверить на тестовом стенде. Не придумывайте параметры, пути и имена служб.
- `${CLAUDE_SKILL_DIR}` — папка этого скила. Если агент не подставляет переменную, скрипты лежат в `scripts/` рядом с этим файлом.

Дополнительно для этого скила:

- Пароли не проверяйте подбором и не просите показать. Про пароль спрашивают, когда и кем он менялся.
- Итог самооценки сам по себе чувствителен: не кладите его в открытые папки и общие чаты.

## Порядок работы

1. **Границы.** Выясните состав контура: серверы RX, база и реплики, брокер, поиск, хранилище, прокси,
   сервер копий; Linux или Windows; Docker или Kubernetes; можно ли запускать скрипт через sudo; где папка
   Directum Launcher (в ней `etc/config.yml`, в примерах справки `/srv/DirectumLauncher`). Список серверов
   пойдёт в итог. Если администратор хочет сначала быстрый взгляд, начните с шага 4 на одном сервере.

2. **Опросник.** Пройдите 22 вопроса по группам, от критичных к низким, по `references/questionnaire.md`.
   Там у каждого вопроса: зачем он, как проверить, норма, что сделать. Список с весами и проверками скрипта:
   `python3 ${CLAUDE_SKILL_DIR}/scripts/score.py --list`.
   - Ответы: да, частично, нет, не знаю. «Не знаю» считается как «нет». Вопросов без ответа не оставляйте.
   - «Да» только с подтверждением: вывод команды, протокол, настройка. Нет подтверждения, это «частично»
     или «не знаю». На этапе опроса не спорьте: расхождения разберёт шаг 5.

3. **Первый подсчёт.**
   ```bash
   python3 ${CLAUDE_SKILL_DIR}/scripts/score.py --answers yyynpyyppnyyyypyynyyyy
   python3 ${CLAUDE_SKILL_DIR}/scripts/score.py q1=да q2=частично q3='не знаю' ...   # или так
   ```
   Строка: по символу на вопрос q1..q22 (`y`, `p`, `n`, `u`, `-` пропуск); подходит и адрес страницы
   `https://drxinfra.ru/security-check.html?a=...`, если администратор отвечал на сайте.
   - Норма: зелёная зона, 80 и выше без открытых критичных. Жёлтая: от 50 до 79. Красная: ниже 50 или любой
     критичный вопрос с ответом «нет» или «не знаю», при любом балле.
   - Код возврата 0 только для зелёной зоны, 1 для жёлтой и красной, 2 нет ответов или ошибка ввода.
   - Красная из-за критичного вопроса: этот пункт идёт в итог первым, не дожидаясь остальных проверок.

4. **Проверка фактами на каждом Linux-сервере.** Спросите согласие на sudo, затем:
   ```bash
   sudo python3 ${CLAUDE_SKILL_DIR}/scripts/host_audit.py \
     --config-dir /srv/DirectumLauncher/etc --config-dir /etc/rabbitmq --tls rx.example.com:443
   ```
   - Без sudo скрипт тоже работает: то, что без root не проверить, помечено ERROR с причиной.
   - Каталоги `--config-dir` подставьте свои: конфигурация Launcher, брокера, базы, прокси. TLS-адреса:
     веб-клиент, база (`pg://хост:5432`), брокер (`хост:5671`), контроллер домена (`хост:636`).
   - Код 0: отклонений нет; 1: есть WARN или CRIT; 2: отклонений нет, но что-то не проверено.
   - CRIT сообщайте сразу: вторая учётка с UID 0, пустые пароли, root входит по паролю, Docker API без
     TLS в сети, истёкший сертификат.
   - Что значит каждая проверка, ложные срабатывания и что даёт root: `references/host-checks.md`.
   - Нужен только один вопрос: `--only sshd`, `--only tls --tls ...`; список проверок: `--list`.
   - Скрипт можно скопировать на сервер вместе с `mask_secrets.py`: нужен только python3.

5. **Сверка ответов с фактами.** У каждой находки скрипта есть номера вопросов (`Вопросы опросника`
   в тексте, `questions` в JSON). Если факт противоречит ответу, например на q8 ответили «да», а
   `sshd.password` WARN на одном из серверов, поменяйте ответ на «частично» или «нет» и запишите причину
   в таблицу расхождений. Если на вопрос ответили «не знаю», а скрипт показал норму, ответ можно поднять
   до «да» только после проверки на всех серверах контура.

6. **Что скрипт не видит.** Пройдите по `references/manual-checks.md` для компонентов из шага 1:
   - PostgreSQL: роли и `rolsuper` учётки RX (q10), `pg_hba.conf`, шифрование по `pg_stat_ssl`;
   - RabbitMQ: guest, права, соединения без TLS; Elasticsearch: отвечает ли без учётных данных;
   - прокси: переадресация на HTTPS, защитные заголовки (q17); консоль Keycloak снаружи (q21);
   - Docker и Kubernetes: изоляция, политики, образы (q16).

   Настройки самой RX (тип входа, политики учётных записей, блокировка по IP, второй фактор, служебные
   учётки Administrator и Integration Service, шифрование параметров config.yml, Directum Launcher с
   `--auth`) смотрите по `references/rx-settings.md` и сверяйте со справкой своей версии через rxmcp.
   Если что-то из этого отдельная большая тема, передайте её профильному скилу: `rx-backup-check` (q1, q2),
   `rx-postgresql` (q10, TLS до базы), `rx-rabbitmq` (guest, TLS до брокера), `rx-elasticsearch`,
   `rx-logs` (q18), `rx-update` (q5, q14).

7. **Пересчёт и итог.** Пересчитайте `score.py` с исправленными ответами (`--json`, если итог собирает
   программа) и соберите итог по `references/result-template.md`. Предложите повторить самооценку через
   квартал или после закрытия первого раздела.

## Что сказать пользователю

Коротко и по делу, в таком порядке:

1. **Итог одной строкой:** балл, зона, сколько отвечено, сколько открытых критичных. Красная из-за
   критичного вопроса называется прямо: «красная зона, потому что нет проверенного восстановления».
2. **Сделать сейчас:** все открытые критичные вопросы и CRIT скрипта. По каждому: что не так, на каком
   сервере, чем подтверждено (проверка скрипта, команда, протокол или «со слов администратора»), что
   сделать. Команды, которые меняют систему, только с предупреждением и способом отката.
3. **Запланировать:** высокие и средние пункты по весу, по одной строке.
4. **Расхождения:** где ответ администратора не совпал с фактами и какой ответ взят в расчёт.
5. **Что не проверено:** серверы без доступа, Windows, проверки без root, вопросы, на которые ответили
   «не знаю».
6. **Строка ответов** и ссылка на страницу с ними, чтобы повторить самооценку позже.

Не называйте самооценку аудитом и не обещайте, что зелёная зона означает защищённость: она означает,
что базовые меры, по словам администратора и проверкам серверов, на месте.

## Справочник

- `references/questionnaire.md`: 22 вопроса, веса, логика зон, как проверить каждый ответ. Шаги 2, 3 и 5.
- `references/host-checks.md`: что проверяет `host_audit.py`, статусы, что меняется без root. Читать на шаге 4.
- `references/manual-checks.md`: команды для PostgreSQL, RabbitMQ, Elasticsearch, прокси, Keycloak, Docker,
  Kubernetes, цепочки поставок, ИИ-помощника и подрядчика. Шаг 6.
- `references/rx-settings.md`: настройки безопасности самой RX со ссылками на статьи справки 25.2. Шаг 6.
- `references/result-template.md`: шаблон итога. Шаг 7.
- `scripts/score.py`: подсчёт балла и зоны, тот же расчёт, что на странице самооценки.
- `scripts/host_audit.py`: проверка Linux-сервера, только чтение.
