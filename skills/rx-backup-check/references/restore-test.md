# Пробное восстановление Directum RX

Цель: доказать, что из копий поднимается рабочая система, и измерить время, то есть фактическое RTO. Без пробного восстановления копия только числится. Делают раз в месяц или квартал и перед каждым обновлением RX. Команды восстановления базы ниже проверены на PostgreSQL 16 в контейнере (pg_probackup 2.5.16, pg_basebackup с архивом `cp`); пути и имена подставьте свои.

## 0. Подготовка

- Отдельная машина или виртуальная машина. Место: размер каталога данных PostgreSQL с запасом, плюс копия хранилища документов.
- Сеть изолирована от рабочего контура: нет доступа к рабочим RabbitMQ, почтовому серверу, интеграциям, сервисам электронного обмена и к рабочему хранилищу или бакету. Поднятый RX начнёт выполнять фоновые процессы и может разослать уведомления или отправить документы наружу.
- Та же мажорная версия PostgreSQL (для `pg_basebackup`, pg_probackup, pgBackRest обязательно), та же версия RX и прикладной разработки.
- Выбрана целевая точка: время, на которое восстанавливаем (например, сегодня 09:00), если есть архив WAL. Без архива точка равна моменту копии.
- Секундомер: время каждого шага записывается в протокол (раздел 6).

## 1. База

Во всех вариантах восстановленный сервер запускают с `-c archive_mode=off`. Копия каталога данных содержит настройки рабочего сервера, в том числе `archive_command`: без этого ключа восстановленный сервер после перехода на новую линию времени начнёт писать свои сегменты в рабочий архив. pg_probackup и `pg_basebackup` копируют каталог данных целиком, вместе с `postgresql.auto.conf` (и с `postgresql.conf`, если он лежит в каталоге данных); на pg_probackup это проверено: `archive_command` с `archive-push` в рабочий каталог переехал в копию.

Параметры, которые на восстановленном сервере должны быть не меньше, чем на исходном: `max_connections`, `max_prepared_transactions`, `max_locks_per_transaction`, `max_wal_senders`, `max_worker_processes`. Иначе восстановление остановится, например с `maximum number of prepared transactions reached` (проверено).

**pg_probackup.** Сначала проверка, потом восстановление на момент времени:

```bash
sudo -u postgres pg_probackup-16 validate -B <каталог> --instance <имя> --recovery-target-time='2026-11-05 09:00:00+03'
sudo -u postgres pg_probackup-16 restore -B <каталог> --instance <имя> -D /restore/pgdata -j 4 \
  --recovery-target-time='2026-11-05 09:00:00+03' --recovery-target-action=promote
sudo -u postgres /usr/lib/postgresql/16/bin/pg_ctl -D /restore/pgdata -o "-p 5433 -c archive_mode=off" -l /restore/log.txt -w start
```

Без `--recovery-target-action=promote` pg_probackup оставляет сервер на паузе в режиме восстановления (только чтение, `pg_is_in_recovery()` вернёт `t`), RX на такой базе не заработает. pg_probackup сам прописывает `restore_command` с `archive-get` из каталога копий. Путь к `pg_ctl` зависит от сборки: в Debian и Astra `/usr/lib/postgresql/<версия>/bin`, в Postgres Pro свой каталог.

**pg_basebackup и архив WAL.** Распаковать копию, указать, откуда брать сегменты и до какого момента:

```bash
mkdir -m 700 /restore/pgdata
tar -xzf <копия>/base.tar.gz -C /restore/pgdata
tar -xzf <копия>/pg_wal.tar.gz -C /restore/pgdata/pg_wal
cat >> /restore/pgdata/postgresql.auto.conf <<'EOF'
restore_command = 'cp <каталог архива>/%f %p'
recovery_target_time = '2026-11-05 09:00:00+03'
recovery_target_action = 'promote'
EOF
touch /restore/pgdata/recovery.signal
chown -R postgres:postgres /restore/pgdata
sudo -u postgres /usr/lib/postgresql/16/bin/pg_ctl -D /restore/pgdata -o "-p 5433 -c archive_mode=off" -l /restore/log.txt -w start
```

Справка RX описывает тот же порядок: для PostgreSQL 12 и новее настройки восстановления пишут в `postgresql.auto.conf` (ra_vosstanovlenie_iz_arhivnoj_kopii.htm); файл `recovery.signal` требует документация PostgreSQL. В журнале при успехе: `starting point-in-time recovery to ...`, `recovery stopping before commit of transaction ...`, `selected new timeline ID`, `archive recovery complete`.

**pg_dump.** Роли, затем база:

```bash
sudo -u postgres psql -p 5433 -f <копия>/globals_<дата>.sql
sudo -u postgres createdb -p 5433 -O <владелец базы RX> <база RX>
sudo -u postgres pg_restore -p 5433 -d <база RX> -j 4 <копия>/<база>_<дата>.dump
```

Справка RX показывает вариант `pg_restore -C -d postgres <файл>` (ra_vosstanovlenie_iz_fajla_arhiva.htm). Дамп восстанавливается и на другую версию PostgreSQL, но долго: индексы строятся заново.

**WAL-G и pgBackRest:** `wal-g backup-fetch /restore/pgdata LATEST` с `restore_command = 'wal-g wal-fetch %f %p'`; `pgbackrest --stanza=<имя> --pg1-path=/restore/pgdata --type=time --target='<время>' --target-action=promote restore`. Конфигурация инструмента на машине восстановления должна смотреть в копию репозитория только на чтение или в сам репозиторий без права записи.

## 2. Проверка базы

```sql
SELECT pg_is_in_recovery();                          -- f: база принимает запись
SELECT gid, prepared FROM pg_prepared_xacts;         -- подготовленные транзакции переезжают в копию и держат блокировки
SELECT count(*) FROM sungero_content_edoc;           -- документы
SELECT max(id) FROM sungero_content_edocversion;     -- последняя версия документа
SELECT relname, n_live_tup FROM pg_stat_user_tables ORDER BY n_live_tup DESC LIMIT 20;
```

Те же запросы на рабочей базе дают ориентир: в копии значения не больше рабочих, разница соответствует работе после целевой точки. На стенде проверки это выглядело так: в копии 200 000 документов, на рабочей базе 210 000, и все 10 000 разницы созданы после копии. Таблицы `Sungero_Content_EDoc` и `Sungero_Content_EDocVersion` описаны в справке (fsd_primery_sistemnykh_tablic.htm); в PostgreSQL их имена в нижнем регистре. Для точной сверки полезно, чтобы скрипт копирования сам записывал такие числа рядом с копией.

## 3. Тело документа: база против хранилища

1. Возьмите версию, созданную незадолго до целевой точки, и посмотрите её поля тела. По справке свойство Body версии раскладывается на колонки `Body_Id`, `Body_Size`, `Body_Hash`, `Body_Storage` (fsd_kolonki_svoistv_komponent.htm); точные имена в своей базе смотрите командой `\d sungero_content_edocversion`.

   ```sql
   SELECT * FROM sungero_content_edocversion ORDER BY id DESC LIMIT 3;
   ```

2. Найдите это тело в восстановленной копии хранилища и в рабочем хранилище. Как тела раскладываются по папкам, справка не описывает: ищите по идентификатору (`find <копия хранилища> -name '*<Body_Id>*'`), путь также есть в отчёте проверки целостности хранилища. Размер файла сравните с `Body_Size`.
3. Сравните хеши файла из копии и из рабочего хранилища: `sha256sum <файл из копии> <тот же файл в рабочем хранилище>`. Алгоритм `Body_Hash` в справке не назван, поэтому сравнивают файлы между собой, а не с этим полем.
4. Если RX на стенде поднят (раздел 4), то же проверяется через систему: скачать версию из восстановленного RX и из рабочего и сравнить `sha256sum`.
5. Массово: с версии 25.2 на стенде запускают фоновый процесс «Проверка целостности данных сервисов хранилищ» (admin_fp_proverka_celostnosti.htm). Пустой отчёт значит, что все тела, на которые ссылается база, нашлись.

## 4. Подъём RX на стенде

- Копия `config.yml` с заменой адресов: `CONNECTION_STRING` на восстановленную базу, `STORAGE_PATH` или параметры S3 на копию хранилища (никогда не на рабочий бакет), `QUEUE_CONNECTION_STRING` на RabbitMQ стенда, почта выключена или направлена в никуда. Пустой `ELASTICSEARCH_URL` отключает индексирование (admin_obshchie_nastroiki_linux.htm).
- Код системы `PRIMARY_TENANT` прежний: при восстановлении базы указывают код ранее развёрнутой системы (admin_minimalnye_nastroiki_linux.htm). Сертификат защиты данных тот же, что в рабочем контуре; при шифровании документов нужен и сервис ключей со своими сертификатами и секретами.
- Если параметры `config.yml` зашифрованы, на стенде нужен пароль шифрования (admin_shifrovanie_parametrov.htm).
- Порядок запуска: СУБД, брокер, хранилище, сервисы RX, веб-клиент. Развёртывание тем же Directum Launcher и той же версией, что в рабочем контуре, по справке своей версии.

## 5. Приёмка

- Вход в веб-клиент. Единый вход в изолированной сети может не работать: используйте локальную учётную запись администратора.
- Документ, созданный незадолго до целевой точки, открывается вместе с телом; документ, созданный после неё, отсутствует. Это подтверждает RPO.
- Задача создаётся, отправляется и приходит исполнителю внутри стенда.
- Поиск работает после перестроения индекса; время перестроения в протокол.
- Время от старта до рабочего веб-клиента и есть RTO.

## 6. Протокол

Образец протокола на вымышленных данных: https://drxinfra.ru/sample-restore-protocol.pdf. Минимальный состав:

| Раздел | Что записать |
|---|---|
| Итог | фактическое RTO, фактическое RPO, результат |
| Исходные данные | целевая точка; базовая копия (дата, размер, инструмент, статус); архив WAL (последний сегмент, целостность); копия хранилища (дата, объём, способ); машина восстановления; версии RX, PostgreSQL, ОС; участники |
| Журнал шагов | время, шаг, длительность, результат |
| Замечания | что пошло не так и что с этим сделано или когда будет сделано |
| Что проверено | число документов, последний документ до точки, тело открывается, задача прошла, поиск |
| Подписи | кто провёл, кто принял, дата следующего восстановления, выполнены ли целевые RTO и RPO |

## 7. Уборка

Остановить стенд (`pg_ctl -D /restore/pgdata -m fast stop`), удалить данные и копию хранилища, освободить диск. Стенд содержал рабочие данные, в том числе персональные: удаление по тем же правилам, что для рабочего контура, и отметка об этом в протоколе.

## Быстрая проверка без стенда

Если отдельной машины пока нет, минимум: восстановить базу в контейнер или во вторую базу на другом сервере и сравнить число таблиц и строк. Генератор https://drxinfra.ru/postgresql-backup.html печатает такую проверку для каждого способа. Это проверяет копию базы, но не хранилище, не конфигурацию и не RTO: полноценное пробное восстановление она не заменяет. Восстанавливать рядом с рабочей базой на том же сервере можно только с согласия: это нагрузка на диск и процессор рабочего сервера.
