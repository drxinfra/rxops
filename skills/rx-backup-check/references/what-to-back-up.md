# Что входит в копию Directum RX

Ссылки вида `имя.htm` ведут на статьи справки Directum RX (проверено по справке 25.2). Справку своей версии открывайте через rxmcp: `rx_help_topic` с именем статьи.

## База данных

- Всё прикладное состояние: карточки, задачи, задания, права, история. Активированная лицензия хранится в базе (таблица `Sungero_System_License`), опубликованная прикладная разработка тоже (`Sungero_IDE_FullDeploy`) (fsd_primery_sistemnykh_tablic.htm).
- Справка для Linux предлагает три способа, которые дополняют друг друга: плановые полные копии, непрерывный архив журнала предзаписи (WAL) и репликацию (ra_rezervnoe_kopirovanie_i_vosstanovlenie_bd_linux.htm). Репликация копию не заменяет: логическую ошибку реплика повторит (ra_replikaciya_bazy_dannyh.htm).
- Дамп одной базы не содержит ролей и их паролей. Рядом с `pg_dump` всегда кладут `pg_dumpall --globals-only`, иначе восстановленная база окажется без владельцев.
- Где база и как она называется, видно в `CONNECTION_STRING` секции `common_config` файла `DirectumLauncher/etc/config.yml` (admin_minimalnye_nastroiki_linux.htm). Читать через маскировщик.

## Хранилище документов

- Содержимое версий документов (тела) лежит не в базе, а в файловом или объектном хранилище под управлением сервиса хранилищ (ar_storageservice.htm). В базе только ссылки: таблица версий `Sungero_Content_EDocVersion` с идентификатором тела (fsd_primery_sistemnykh_tablic.htm, fsd_kolonki_svoistv_komponent.htm).
- Файловое хранилище: путь в параметре `STORAGE_PATH` сервиса хранилищ, локальная или сетевая папка (admin_nastroika_khranilishcha_linux.htm). Хранилищ может быть несколько, у каждого свой экземпляр сервиса (admin_nastroyka_hranilish_linux.htm): копируют все.
- Объектное хранилище S3: адрес, ключи и имя бакета задаются параметрами `S3_STORAGE_*`, имя бакета по умолчанию равно коду системы `PRIMARY_TENANT` (admin_perehod_na_isp_obyekt_hr_linux.htm). Копию бакета делают версионированием и репликацией на стороне хранилища или зеркалом в другое хранилище.
- Для файлового хранилища на Linux справка описывает копирование через Bacula и требует держать хранилище и его копии на разных серверах (admin_nastroika_rezervnogo_kopirovaniia_linux.htm, admin_rezervnoe_kopirovanie_papki_fh.htm).
- Заменённые и удалённые тела сервис хранилищ сначала переносит в папку `deleted` и удаляет через срок `OBSOLETE_DATA_LIFE_PERIOD` (по умолчанию 3 дня), если на них не осталось ссылок; отдельные сроки задают `TRANSIENT_DATA_LIFE_PERIOD` и `DELETED_DATA_LIFE_PERIOD`. Справка прямо связывает этот срок с частотой копий: чем он короче, тем чаще нужны копии (admin_nastroika_khranilishcha_linux.htm). Копируйте папку хранилища целиком, вместе с `deleted`.

## Согласованность базы и хранилища

Восстановиться можно только из согласованной пары. Порядок: сначала копия базы, затем хранилища, в одно окно. Тогда всё, на что ссылается база, есть в копии хранилища, а лишние файлы безвредны.

Если пара разошлась (база из одной ночи, хранилище из другой), признаки и порядок разбора:

- версии с телами, которых нет в хранилище: с версии 25.2 их находит фоновый процесс «Проверка целостности данных сервисов хранилищ», по умолчанию раз в неделю, отчёт в карточке хранилища (admin_fp_proverka_celostnosti.htm, разбор отчёта: https://drxinfra.ru/errors/rx-storage-integrity-violated.html);
- для ручного восстановления справка описывает колонки `PreviousBodyId`, `PreviousPublicBodyId` и сведения о шифровании в таблице `Sungero_Content_DocHistory` (sds_khranenie_informatcii_o_predydushchikh_telakh.htm). Это работа с данными: только с разработчиками и на копии.

## Конфигурация и секреты

| Что | Где | Зачем |
|---|---|---|
| `config.yml` | `DirectumLauncher/etc/config.yml` (admin_nastr_config_linux.htm) | все настройки системы; из него генерируются настройки сервисов (admin_konfigurirovanie_nastroek_linux.htm) |
| папка с данными `home_path` | переменная в `config.yml` (admin_minimalnye_nastroiki_linux.htm) | подпапки содержимого документов, журналов, предпросмотра; что из неё можно не копировать, проверяйте на тестовом стенде |
| код системы `PRIMARY_TENANT` | `common_config` | при восстановлении базы указывают код ранее развёрнутой системы (admin_minimalnye_nastroiki_linux.htm) |
| сертификат защиты данных Sungero data protection | `DATA_PROTECTION_CERTIFICATE_FILE` или `_THUMBPRINT` в `common_config` (admin_web_server_linux.htm) | шифрование cookie и проверка токенов; у всех сервисов он должен совпадать |
| сертификат HTTPS | `ssl_cert` в секции `SungeroHaproxy` (admin_minimalnye_nastroiki_linux.htm) | вход по HTTPS |
| пароль шифрования параметров | переменная окружения из `config_password` (admin_shifrovanie_parametrov.htm) | без него зашифрованные строки подключения в копии `config.yml` не прочитать |
| сертификаты и секреты сервиса ключей | сервис ключей, если включено шифрование документов | справка требует хранить копии сертификатов шифрования и секретов сервиса, причём отдельно друг от друга: без них документы не расшифровать даже из копии (admin_zamena_kluchey_shifrovaniya_linux.htm) |
| файл ключа лицензии | у администратора | активированная лицензия в базе, файл пригодится при переносе (admin_activacia_key_licencii.htm) |

Секреты (пароли, закрытые ключи) хранят в хранилище паролей или сейфе, а не рядом с копиями данных: копия, которую украли вместе с ключами, раскрыта целиком.

## Что можно не копировать

- Индекс Elasticsearch: строится заново из базы (первоначальное индексирование, admin_pervonachalnoe_indeksirovanie_linux.htm). Время перестроения записывают в протокол пробного восстановления: пока оно идёт, поиск не работает. Если время неприемлемо, добавляют снимки индекса средствами Elasticsearch.
- Журналы сервисов: для восстановления не нужны, но их срок хранения задаёт требования к месту.

Что не может заменить копию:

- снимок виртуальной машины: одна точка «как при выключении питания», обычно на той же площадке, вернуться на произвольный момент нельзя;
- реплика: удаление и порча данных применяются на ней так же быстро.
